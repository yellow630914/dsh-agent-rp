# [Feature] 在资源中心直接编辑世界书条目

### 这个能力解决什么问题？

世界书

资源中心里的世界书只能导入、设为默认、删除——**不能改**。想调一句触发词、
补一条设定、或者删掉一条写坏的条目，只能回到原始 JSON 文件里改，再重新导入一次；
而重新导入出来的是**另一本**世界书，绑定它的角色卡不会跟过去，还得手动重绑。

会话设定里那个世界书编辑器只作用于**当前会话的覆盖层**，改不到来源本身，
也没有「新增条目」。

### 期望的行为

1. 资源中心每一本世界书旁边有「编辑」，点开可以直接改条目
2. 编辑窗口**参照会话设定-世界书的编辑方式**，不要另起一套
3. 编辑窗口要能**新增条目**和**删除条目**
4. 世界书如果和角色卡绑定，改世界书的同时角色卡绑定的那本也要是新的

### 关于第 4 点：角色卡到底绑了什么

导入角色卡时，卡里内置的 `character_book` 会被拆成一本**独立世界书资源**，
角色卡通过 `CharacterWorldBindingStore` 用 **id 引用**它——**不是复制一份**。

- 新会话开始时从 `worldInfos.asset(id)` 读当前内容
- 导出角色卡时 `exportModified` 用绑定的那本世界书**重建** `character_book`

所以只有一份，不存在「两边都要改」。真正要保证的是另一件事：**编辑之后绑定不能断**。

### 补充：采用的实现

世界书 id 是**内容的 sha256**——这正是重复导入同一个文件会自动去重的原因。
所以编辑**不可能保留原 id**：真保留了，以后有人导入**原始那个文件**，
哈希算出来是这个 id、发现文件已经在，就会拿到**编辑后**的内容。

于是编辑走的是「**换身分**」：`WorldInfoLibrary.update()` 是一次事务，

**写新世界书 → 改写全部角色绑定 → 搬移 `.default` 标记 → 退休旧的**

这个顺序是为了崩溃安全：中途断在任何一步，最坏只是留下一个没人引用的世界书文件，
**绝不会出现指向不存在世界书的绑定**。

`CharacterWorldBindingStore.replaceWorldInfoId()` 负责改写绑定，
provenance 原样保留——`embedded-import` 编辑后仍然是 `embedded-import`，
变的是文字，不是这本书**从哪来**。

挡掉了一个边界情况：编辑后的内容如果**刚好等于另一本已被角色绑定的世界书**，
直接拒绝。否则内容地址一致就会静默合并两本书，把别人的绑定一起吃掉。

### 补充：为什么格式知识全留在 Host 端

社区世界书常常带着这个 runtime 没有建模的字段（`probability`、
`extensions` 里的自定义开关……）。存回去的时候如果按 runtime 的模型重新序列化，
这些字段就**被静默丢掉了**——这是最容易把别人的世界书写坏的地方。

所以浏览器只送结构化条目，每一行带一个 `sourceIndex` 说明**它来自哪个原始条目**，
Host 用既有的 `projectedEntry` 把那个原始 JSON 对象带过去。
没有 `sourceIndex` 的行就是新增，省略掉某一行就是删除。

新增的条目 uid 接着这本书自己的编号往下排，而不是漏出 runtime 内部的行名——
编辑过的世界书导出去，读起来还是一本普通的 SillyTavern 世界书。

### 补充：和会话设定里那个编辑器的区别

沿用了同一套 `WorldInfoEditableEntry` 类型和同样的表单结构，但**作用对象不同**：

| | 会话设定 | 资源中心（本次） |
| --- | --- | --- |
| 改的是 | 不可变导入书上的**覆盖层** | **来源本身** |
| 删除 | 可还原的开关 | **真删** |
| 新增条目 | 没有 | 有 |

所以「新增／删除条目」在资源中心是**新能力**，不是把会话版搬过来。

### 补充：已经开始的会话不受影响

会话在启动时把世界书**无损快照**写进了自己的事件日志，之后再也不读资源库。
这是刻意的：正在玩的那局不会因为你在资源中心改了一句话而中途变样。
想让改动生效，开新会话。
