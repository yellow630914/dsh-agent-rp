# 原生状态方案与状态栏

状态数据不再依赖 SillyTavern 的变量体系。一个**原生状态方案**声明会话保存哪些 JSON 字段、
结算时遵守什么规则，以及状态栏怎么呈现；它由 Agent RP 自己拥有，不需要世界书条目，
也不执行任何外部脚本。导入了 MVU 变量卡的会话继续走原有适配器，两条路径互不影响。

## 三样东西，三种寿命

| | 存在哪 | 能不能事后改 |
|---|---|---|
| 初始 JSON 与结算规则 | 会话启动时冻结成 `agent-rp/state-scheme-seed` | **不能**——它们是模型可见的，改了旧会话就重放不出同样结果 |
| 状态值 | `agent-rp/state` 修订，CAS 递增 | 只能追加新修订 |
| 状态栏模板 | 资源中心的方案库文件 | **能**——纯展示层，旧会话重开即套用新模板 |

这条界线是整个设计的核心：**模板只读投影**，不进 `renderRoleplayStateContext`，
也不进结算请求。否则玩家改一个模板就改了重放结果。

## 方案与状态值

方案从「资源中心 → 状态方案」创建，保存在 `~/.dsh/agent-rp/state-schemes/<id>.json`，
按 revision 检查覆盖。启动会话时选中的方案会被冻结成 seed 事件；模板留在库里，
按方案 id 现查。库里没有方案时，内置的「Agent RP · 基础状态」始终可选。

状态命名空间归 `roleplay:state-scheme` 所有。和其他原生状态一样，只有所有者模块或玩家
（`rp-state` 命令）能写，`adapter:mvu` 写不进去。第一次结算之前没有 `agent-rp/state` 记录，
此时读到的是方案冻结的初始值，修订号为 0。

## 结算

`state-settlement` Worker 不认识 MVU，它只看当前回合的计划里有没有状态契约。
契约的来源现在有两个：导入卡的 MVU 规则（`engine: 'mvu-v0'`），或原生方案的冻结规则
（`engine: 'native-v0'`）。两者共用同一套语义操作和同一个候选加独立核验的流程，
详见[多 Agent 回合 Worker](multi-agent-turn-workers.md)。

结算结果的写入方式按引擎分流：MVU 归约进 `agent-rp/mvu-state` 快照，
原生方案走 `appendRoleplayState` 的 CAS 写入。原生方案的重入检测不靠逐回合标记，
而是看修订号——命名空间一旦越过本回合准备的修订，说明结算已经落盘或被玩家编辑取代，
两种情况都不该再写一次。

## 结算节奏

「设置 → Agent RP → Agent 工具策略 → 状态结算」有三档：

- **关闭**——不准备状态契约，状态只能手动编辑
- **仅手动触发**——仍然准备契约（否则手动重算没有基线），但自动 Worker 不跑
- **每回合结算**（默认）——正文结束后由后台 Worker 结算

刻意**没有**「强制模型每回合调用状态工具」这一档。内联工具每回合要多写
`tool/call` 与 `tool/result` 两条 surface 事件和一列 transcript，还会打断可复用的前缀缓存；
后台 Worker 走的全是没有 `surfaceOp` 的插件事件，结果一样而代价低一个量级。

## 手动重新结算

状态栏上有两个动作，它们的代价完全不同：

- **重新渲染**——重新载入模板并重绘。纯客户端，不写任何事件。
- **重新结算**——重跑一次模型计算并写入新修订。

重新结算复用同一个 `runRoleplayStagedStateSettlement`，不存在第二套结算程序；
只有两处不同：

1. **基线**。新值从这一回合**准备时**的修订算起，而不是从命名空间当前的值算起。
   否则 `delta` 会被套用两次（体力 -10 变成 -20）。SessionLog 只能追加，
   所以结果写成下一个修订，而不是回退日志。
2. **证据取自哪一层**。自动结算读 canonical surface；手动结算读 Agent RP overlay
   （`roleplaySurfaceNodes`），因为只有 overlay 跟得上回复版本切换，
   而玩家看的就是他自己选中的那一版。见[对话记录的分层](transcript-layers.md)。

`force` 同时跳过按 `throughEventSeq` 的去重——去重是为了防止自动流程重复劳动，
显式请求恰好是相反的意图。

## 状态栏

面板挂在输入框上方的 composer dock 里，和酒馆状态栏同一个位置，可折叠。
折叠状态存在工作区设置的 `statePanel.collapsed`，**不进 Session**，
所以折叠、展开、换模板都不碰重放、楼层或前缀缓存。

模板语言是声明式的，不执行 JS：

| 写法 | 含义 |
|---|---|
| `{{/路径}}` | 按 JSON Pointer 取值 |
| `{{.}}` / `{{./字段}}` | 当前循环项，或它的字段 |
| `{{@}}` | 当前循环的键或下标 |
| `{{#/路径}}…{{/}}` | 遍历数组或对象 |
| `{{?/路径}}…{{/}}` | 值存在且非空时渲染 |
| `{{!/路径}}…{{/}}` | 反之 |

**取不到的路径渲染成空，不报错**——否则改一次 schema 就会打爆所有旧会话的面板。
渲染是模板与状态的纯函数：没有时钟、没有随机数、没有脚本，同样的状态永远得到同样的面板。

三种格式：`html` 经 DOMPurify 后进严格 CSP 的 sandbox iframe；`markdown` 先转 HTML 再走同一条路；
`text` 包进 `<pre>`。HTML 格式下填入的值会被转义，模板自己的标签不会。
模板来自本地库而不是角色卡，所以走的是严格外壳，不开角色卡兼容层的 capability 通道。

## 不影响楼层与聊天记录

结算写的全是没有 `surfaceOp` 的插件事件，五层投影都看不见。内联工具的 `tool/result`
确实进模型 surface 和人类 transcript，但 `surfaceRole()` 对它返回 `undefined`，
`floorProjection` 与 `visibleTavernMessages` 都会滤掉——**楼层编号和酒馆 `message_id` 不会错位**。
`tests/roleplay-state-scheme.test.ts` 有两条回归专门钉死这件事。
