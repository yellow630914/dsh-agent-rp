# 另开分支时补全记忆，停用 replace 版的隐藏楼层（2026-10-03）

楼层面板现在只做一件事：**选一层另开分支**。分支之前可以让一个后台 Worker 读完目前
保留的全部聊天记录、把还没进记忆的事件接着记下去；结果先给玩家看，不满意可以写一段要求
重新补全，确认后才带进新会话。原本用 `replace` 改写当前会话的「隐藏楼层」停用。

同一目录下有对应的需求单。

---

## 流程

1. 面板上拖滑杆选「从第 N 层开始另开分支」
2. 「补全记忆后分支」→ Host 读**目前保留的全部楼层** + 全部现有记忆，向模型要一份补全
   （和 N 无关，见下面「读哪些楼层」）
3. 面板列出每一条时间线条目：**新增**，或**更新**（接着上一条没记完的那一天，附原文对照），每条可取消勾选
4. 不满意：在下面写要求，「重新补全」——这次请求会带上屏幕上的整份提案和这段要求
5. 「创建分支」→ 勾选的条目并进新会话的记忆

「直接分支」保留，行为和以前一样；模型不可用时不会卡住分支。

## 什么都不写进来源会话

提案是**无状态的预览**：补全请求不往来源会话追加任何事件。它唯一变成持久数据的地方是
新会话的 `agent-rp/memory-seed`——分支请求多了一个可选的 `memory` 栏位，Host 把它按主题
并进「当前有效记忆」之后再写种子。

这样做的原因：

- 「分支不动当前会话」这条性质原样保住
- 记忆不需要第四种写入来源。现有三种（`remember` 工具调用、`rp-memory` 命令、种子）都要
  严格校验自己的来源事件，而 `readAgentRpMemoryHistory` 遇到校验不过的记录会直接抛错、
  且跑在每一回合的提示词路径上。种子本来就接受任意条目，所以这里一行校验逻辑都没加
- 不需要「整理到第几层」的水位：时间线自己就说明了记到哪里

代价是来源会话里查不到这次补全的请求与结果。玩家接受的那份结果在新会话的种子里。

## 读哪些楼层：全部，而不是被留下的那一段

玩家的用法是「记忆走在裁切前面」：

```
玩到第 150 层要记忆了；之前的记忆记到第 100 层；前 50 层早就裁掉了
→ 给模型读的是第 50~150 层 + 全部记忆
→ 模型自己对出记到哪里，新写出来的记忆覆盖第 100~150 层
```

所以补全请求里**没有分支点**：它总是读完目前保留的全部楼层，一直记到最后一层。从哪里
接着记由模型对照时间线判断，不由程序切。分支从第几层开始是另一件事——不管切在哪，被裁掉
的那一段都已经在记忆里。

也因此面板上「补全记忆后分支」不需要先选留下几层，提案出来之后滑杆也还能拖。

## 记忆格式：一条接着写的时间线

补全写出来的不是「一个主题一条」的笔记，而是按故事内时间往下接的时间线。格式是玩家定的：

```
【圣龙曆852年4月28日 12:00 ~ 圣龙曆852年4月30日 18:00】      ← 标题：这一条覆盖的起止时间
[4月28日 12:00] 白露带旅人进入王都，在东门被卫兵盘问后放行。  ← 每个场景事件以时间开头
[4月30日 18:00] 两人在钟楼下约定，雨停之后一起去北境。        ← 约 20~50 字
```

- 标题用故事内时间；一条**至少覆盖完整的一天**，事件稀疏的连续几天合成一条
- 一条里有多个场景事件，每个事件开头标出自己的时间
- 只记**还没记过**的事件：全部现有记忆（时间线 + 其它记忆）和目前保留的全部楼层都给
  模型读，它先找到记到哪里，再从那之后接着记到最后一层

模型回传的是结构化数据（`title` / `events[{time, text}]` / 可选的 `replaces`），每一行由
Host 排成 `[时间] 描述`、标题由 Host 套上 `【】`。这样「每个事件以时间开头」是程序保证的，
不是靠模型自觉。条目的 `kind` 一律是 `event`；判断一条记忆是不是时间线条目的规则是
「`event` 且标题被 `【】` 包住」。

### 一天还没记完就分支了怎么办

「同一天不拆成两条」和「上一次可能只记到一天中间」会冲突：上一次记到午后就停了，这一次
的楼层接着同一天。这时模型输出一条**替换**上一条的条目，`replaces` 填它原来的标题——因为标题
就是起止时间，延长之后标题会变，光靠标题对不上。分支请求的 `memory` 因此带一个可选的
`replaces`，`mergeAgentRpMemorySeedEntries` 先按它找，找不到再按自己的标题找，都没有就追加
到末尾。原地替换，所以时间线的顺序不变。

### 故事内时间从哪来

用原生状态方案的会话里，时间在**状态数据**里（例如 `/时空/日期 = 第4天`、
`/时空/时间 = 夜晚`），正文里只有「午后的光」这类文字线索。所以证据里每一层后面会附上
「这一层结束时状态数据里的时间」——`memoryCompletionTimeMarkers` 读每一笔 `agent-rp/state`，
挑出键名像时钟或历法的短标量，时间有变化才标一次。

两个刻意的限制：

- 挑栏位靠的是**键名**（时间 / 日期 / 时空 / 星期 / time / date…）加「值不超过 40 字」。
  这是启发式的：状态方案用了别的键名就不会被认出来，那时模型只能靠正文推断
- 第一层之前的状态修订不算。分支会把带过来的状态写在聊天记录前面，那是保留楼层**结束**时
  的时间，标在第一层上会误导

提示词要求沿用故事自己的历法与写法，正文只给到「清晨 / 夜晚」就写时段，**不编造钟点**。

### 长度

两个数字刻意不一样：

- **程序上限 1500 字**（`AGENT_RP_MEMORY_TEXT_MAX_LENGTH`）。一条记忆正文的硬上限从 1000
  提到 1500，全插件共用——`remember`、记忆面板、导入、种子都一样，面板的输入框也跟着改
- **给模型的指引不变**：每个事件 20~50 字，整条控制在 1000 字以内

中间那 500 字是给事件多的一天超出用的，超一点不会整天被拒。事件太多时提示词要求**不丢
事件**，改为舍弃描述里的细节、把每个事件写短。超过 1500 的条目才会被拒绝并计入
`rejectedCount`，面板会提示「那段时间没有记上」。

放宽上限的代价：含有超过 1000 字记忆的会话，旧版插件读不了（每一回合的提示词都会失败），
所以这一版之后不能直接退回旧版。

解析时逐条判断：

- 和现有条目一字不差的**静默丢掉**（不是提案，也不算错）
- 缺标题、没有事件、事件缺时间或描述、过长、标题重复、两条抢着替换同一天、超过 40 条的，
  计入 `rejectedCount`
- 被输出额度截断的回复用 `jsonrepair` 收尾，保住已经完整的条目

## 请求长什么样

和其他后台 Worker 一样：短 system prompt、不带角色卡 / 世界书 / 酒馆预设，直接
`ctx.llm.stream()`，推理强度经 `negotiateWorkerReasoningEffort` 协商（要 `off`，模型
关不掉时降到它接受的最低档并多留输出额度）。

只继承会话的 **provider / model**，不继承采样参数、`stop` 和输出上限——那些是为正文选的，
会把 JSON 截断。会话还没发过请求时（刚导入、刚分支）依次退到待用的模型选择、部署默认值。

回合进行中拒绝补全：还在串流的回复会被当成一层完整的楼层读进去。

## 顺带修掉：改过记忆的会话分支后整个坏掉

做这个功能时发现分支本来就有一个问题，而且正好在这条路径上。

玩家在回合之间用记忆面板新增 / 纠正 / 忘记 / 导入记忆，会留下 `command/run` +
`command/done`，后者用 seq 引用前者。分支把「回合之外的事件」原样保留并**重新编号**，
引用就指到了别的事件上，`readAgentRpMemoryHistory` 抛
「记忆操作结果没有对应的命令来源」——而它跑在提示词路径上，所以**新会话每一回合都失败**。

另一半：就算引用对得上，这些记录和分支新写的种子也会把同一批记忆套用两次；分支的分支
还会把上一次的种子再套一次。

现在分支时把所有建立记忆的回合外记录（`agent-rp/memory-seed`、`rp-memory` 的命令事件）
都拿掉，只留下那一笔写着完整有效集合的新种子。来源会话不受影响。

## 隐藏楼层停用

`executeTavernHelperMutation` 在解析完请求后立刻拒绝 `set-chat-hidden`，这是面板和脚本
`/hide` 都要经过的唯一入口。面板上的隐藏按钮、确认步骤和 `manageFloors` 一并移除；
`rp-tavern-variables` 命令不再需要 token meter 的估算器，那段接线也拿掉了。

保留的部分：

- `tavern-chat.ts` 的 `setHidden` 本体和它的测试——已经隐藏过楼层的旧会话仍按那个形状
  重放，测试也还要造得出那种日志
- 投影的 `shadowedSeqs`、`hiddenPrefix` 折叠——同样是为了旧会话
- 面板上，早先隐藏过的楼层照旧显示成划线，滑杆下限仍是已隐藏的层数

**对第三方酒馆脚本的影响**：调用 `/hide` 的脚本现在会收到明确的错误讯息。`/unhide` 从
9 月 14 日起就已经是错误。

## 实机验证

2026-10-04 在本机起了一个 DSH 0.2.0-rc.1 的测试 Host（3081 端口、独立的数据目录），装的
就是这份 `lib/`。玩家在上面实测过补全与分支之后才决定部署；测了哪些会话、模型写出来的
时间线长什么样，没有记录在这里。

Host 端自动化测试覆盖不到的仍然是模型本身：时间标得准不准、会不会老实从时间线的末尾接着
记、长聊天记录下要等多久，取决于所选模型和具体的会话。

  `--config-loader native` 加 `--experimental-strip-types` 重建；产物的差异只落在这次

## 已知取舍

- 补全是**一次请求**读完目前保留的全部楼层，包括记忆已经记过的那一段——从哪里接着记是
  交给模型判断的，所以那一段省不掉。它们原本都在上下文里，放得进窗口；但楼层很多时这一次
  请求会很大、要等一阵子。
- 早先被隐藏的楼层不在聊天记录里，补全读不到它们。
- Worker 不带酒馆预设，能不能照常处理内容取决于所选模型，和状态结算 Worker 的情况相同。
